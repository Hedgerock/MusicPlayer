# Создание пустого плейлиста

Статус: В разработке.

## Цель

Пользователь создаёт именованный плейлист для последующего добавления музыки.

## Границы функции

Функция включает ввод названия, проверку данных, сохранение пустого плейлиста на устройстве и отображение
результата в списке плейлистов.

Добавление композиций, переименование и удаление плейлиста реализуются отдельно.

## Правила

- Название плейлиста обязательно.
- Пробелы по краям названия удаляются перед проверкой и сохранением.
- Название, которое после удаления пробелов становится пустым, считается недопустимым.
- Регистр букв и пробелы внутри названия сохраняются.
- Одинаковые названия разрешены.
- Каждый плейлист получает уникальный идентификатор.
- Новый плейлист не содержит композиций.
- Созданный плейлист сохраняется локально и доступен после перезапуска приложения.
- Для создания плейлиста подключение к интернету не требуется.

## Основной сценарий

1. Пользователь открывает форму создания плейлиста.
2. Пользователь вводит название в поле "Название плейлиста".
3. Пользователь нажимает кнопку "Создать".
4. Приложение проверяет название.
5. Приложение сохраняет плейлист на устройстве.
6. Созданный плейлист появляется в списке.

## Обработка ошибок

При недопустимом названии приложение показывает сообщение: "Введите название плейлиста".

Недопустимые данные не передаются на сохранение.

При ошибке сохранения приложение показывает сообщение: "Не удалось сохранить плейлист. Попробуйте ещё раз".

Введённое название сохраняется в форме. Пользователь может повторить попытку без повторного ввода.

Приложение сообщает об успешном создании только после успешного сохранения плейлиста.

## Доступность

- Поле ввода имеет постоянную видимую подпись.
- Кнопка создания содержит текст "Создать".
- Поле и кнопка доступны через TalkBack и имеют понятные названия и соответствующие роли.
- Сообщения об ошибках доступны через TalkBack.
- Ошибки обозначаются текстом, а не только цветом.
- Интерфейс поддерживает системное увеличение шрифта без потери текста и доступа к действиям.
- Область нажатия кнопки составляет не менее 48 x 48 dp.

## Модель и контракт хранилища

Плейлист содержит идентификатор, нормализованное название и упорядоченный список идентификаторов композиций.

При создании список композиций пуст.

Идентификатор не зависит от названия плейлиста.

Контракт PlaylistRepository размещается в application/ports.

Операция add добавляет новый плейлист. Она завершается успешно после завершения сохранения.

Повторяющиеся названия разрешены. Попытка добавления плейлиста с уже существующим идентификатором завершается ошибкой и
не заменяет существующий плейлист.

Операция getAll возвращает все сохранённые плейлисты. Для пустого хранилища она возвращает пустой список.

Ошибки операций репозитория передаются через отклонение Promise.

## Сценарий приложения

Сценарий createPlaylist размещается в application.

Репозиторий и генератор идентификаторов передаются сценарию явно.

Название проверяется до генерации идентификатора и сохранения.

При недопустимом названии сценарий возвращает EMPTY_NAME и не обращается к зависимостям.

При успешном сохранении сценарий возвращает созданный плейлист. Ошибка генерации идентификатора или сохранения приводит к
результату CREATE_FAILED.

Юнит-тесты сценария проверяют успешное создание, недопустимое название и ошибки зависимостей. Репозиторий и генератор
идентификаторов в этих тестах подменяются.

## Репозиторий в памяти

Реализация createInMemoryPlaylistRepository размещается в infrastructure.

Каждый экземпляр содержит собственный набор плейлистов. Данные существуют в течение жизни экземпляра.

Повторный идентификатор отклоняется без замены существующего плейлиста. Одинаковые названия разрешены.

Репозиторий копирует плейлист и массив идентификаторов композиций при добавлении и чтении.

Интеграционные тесты соединяют сценарий создания, валидатор названия и репозиторий в памяти. Генератор идентификаторов
заменяется детерминированной реализацией.

Проверка сохранности после перезапуска остаётся открытой до реализации постоянного хранилища.

## Схема SQLite

Определение первой миграции размещается в `infrastructure/sqlite/migrations/0001-create-playlists.ts`.

Миграция содержит создание таблиц `playlists` и `playlist_tracks`. Структура соответствует ADR-0003.

Интеграционные тесты схемы выполняют SQL через `node:sqlite`. Каждый тест использует отдельную базу в памяти.

Проверки охватывают одинаковые названия, уникальность идентификатора, обязательность идентификатора, порядок и повторения
композиций, уникальность позиции внутри плейлиста, внешние ключи, неотрицательные позиции и каскадное удаление.

Эти тесты проверяют SQL-схему. Применение версий миграций, сохранность файла базы и работа через OP-SQLite проверяются отдельно.

## Применение миграций

Общий механизм `migrateDatabase` размещается в `shared/infrastructure/sqlite`.

Реестр миграций приложения размещается в `app/storage/migrations.ts`.

Номера миграций образуют непрерывную последовательность, начиная с единицы. Некорректный реестр отклоняется до обращения к базе.

Механизм читает `PRAGMA user_version` и применяет только новые миграции.

Каждая миграция и обновление версии выполняются в отдельной транзакции. Ошибка отменяет изменения этой миграции. Ранее
завершённые миграции сохраняются.

База с неподдерживаемой более новой версией отклоняется без изменения её версии и данных.

Внешние ключи включаются при каждом вызове механизма, в том числе при отсутствии новых миграций.

Миграции выполняются до использования соединения репозиториями. Вызовы для одного соединения выполняются последовательно.

Открытие и закрытие соединения остаются ответственностью вызывающей стороны.

Юнит-тесты проверяют некорректные номера миграций и значения версии базы.

Интеграционные тесты используют настоящий SQLite через тестовый адаптер и проверяют создание схемы, повторное применение,
последовательность миграций, откат и сохранность данных.

Механизм миграций используется при инициализации рабочей базы приложения.

## Инициализация соединения

Функция `initializeAppDatabase` размещается в `app/storage`.

Функция получает операцию открытия базы и использует имя `music-player.sqlite`.

Соединение возвращается вызывающей стороне после успешного завершения миграций. Конкретный тип соединения сохраняется.

При успешной инициализации соединение остаётся открытым. Дальнейшее управление его временем жизни выполняет вызывающая сторона.

При ошибке миграций выполняется попытка закрытия соединения. Ошибка закрытия не подменяет исходную ошибку инициализации.

При ошибке открытия миграции не запускаются.

Юнит-тесты проверяют открытие, ожидание миграций, передачу готового соединения и обработку ошибок. Механизм миграций в них
подменяется.

Интеграционные тесты используют настоящий механизм миграций и SQLite через тестовый адаптер `node:sqlite`.

## Готовность хранилища при запуске

Функция `getAppDatabase` размещается в `app/storage` и открывает рабочую базу через OP-SQLite.

Загрузчик `createAppDatabaseLoader` начинает инициализацию при первом обращении. Одновременные обращения к одному экземпляру
загрузчика используют общую попытку инициализации.

Успешно инициализированное соединение сохраняется для последующих обращений. После ошибки следующее обращение запускает новую
попытку.

Корневой компонент ожидает готовности хранилища перед отображением содержимого приложения.

Во время ожидания отображается сообщение "Готовим приложение...". При ошибке отображается понятное сообщение и кнопка
"Повторить".

Размонтирование компонента прекращает обновление его состояния. Готовое соединение остаётся под управлением приложения.

Юнит-тесты проверяют отложенный запуск, совместное ожидание и повторную попытку после ошибки.

Интеграционный тест проверяет совместные обращения с настоящими миграциями и SQLite.

Компонентные тесты проверяют ожидание готовности и успешный повтор после ошибки.

## Репозиторий SQLite

Реализация `createSQLitePlaylistRepository` размещается в `infrastructure/sqlite`.

Репозиторий получает готовое соединение после применения миграций. Открытие, миграции и закрытие соединения остаются
ответственностью приложения.

Добавление плейлиста и всех его композиций выполняется в одной транзакции. Ошибка любой записи отменяет всю операцию.

Значения передаются параметрами SQL-запросов.

Позиции композиций назначаются последовательно, начиная с нуля. Чтение сохраняет порядок и повторения идентификаторов.

Чтение выполняется в отдельной транзакции. Пустые плейлисты возвращаются с пустым массивом `trackIds`.

Юнит-тесты проверяют передачу ошибок и отклонение некорректных результатов чтения.

Интеграционные тесты используют настоящий репозиторий, миграции и SQLite через адаптер `node:sqlite`. Они проверяют создание
через сценарий приложения, сохранение значений с кавычками, порядок композиций, повторения, одинаковые названия, повторный
идентификатор, атомарный откат и сохранение снимка входных данных.

Проверка сохранности пользовательских плейлистов после перезапуска Android-приложения выполняется после подключения репозитория
к приложению.

## Критерии приёмки

### Создание плейлиста

Дано: пользователь ввёл название "Дорога".

Когда: пользователь создаёт плейлист и сохранение завершается успешно.

Тогда: в списке появляется пустой плейлист с названием "Дорога".

### Удаление пробелов по краям

Дано: пользователь ввёл название " Дорога ".

Когда: создание плейлиста завершается успешно.

Тогда: сохраняется название "Дорога".

### Недопустимое название

Дано: поле названия пустое или содержит только пробелы.

Когда: пользователь нажимает "Создать".

Тогда: приложение показывает сообщение "Введите название плейлиста" и не выполняет сохранение.

### Одинаковые названия

Дано: существует плейлист с названием "Дорога".

Когда: пользователь успешно создаёт еще один плейлист с таким же названием.

Тогда: существуют два отдельных плейлиста с разными идентификаторами.

### Ошибка сохранения

Дано: пользователь ввёл допустимое название.

Когда: сохранение завершается ошибкой.

Тогда: приложение сообщает об ошибке, сохраняет введённое название в форме и позволяет повторить попытку.

### Перезапуск приложения

Дано: пользователь успешно создал плейлист.

Когда: пользователь закрывает приложение и запускает его заново.

Тогда: созданный плейлист присутствует в списке.

## Проверка функции

Юнит-тесты проверяют нормализацию и валидацию названия.

Интеграционные тесты проверяют взаимодействие сценария создания с репозиторием, включая успешное сохранение
и обработку ошибки. Проверка сохранности данных использует реальное локальное хранилище.

Компонентные тесты проверяют ввод названия, отправку формы и отображение ошибок через доступные пользователю
элементы.

Названия автоматизированных тестов записываются на английском языке. Сценарии следуют структуре
Given / When / Then.

На эмуляторе или устройстве проверяются создание плейлиста, сохранность после перезапуска, работа с
TalkBack и системное увеличение шрифта.
