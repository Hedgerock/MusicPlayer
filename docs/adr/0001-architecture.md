# ADR-0001: Архитектура приложения

## Статус

Принято.

## Контекст

MusicPlayer — музыкальный плеер для файлов на устройстве. Основная платформа — Android. Поддержка iOS рассматривается как
дальнейшее развитие.

Приложение включает музыкальную библиотеку, воспроизведение, плейлисты и историю.

Правила этих функций должны проверяться unit- и integration-тестами. Работа с Android, хранилищем и аудиодвижком требует
отдельных реализаций и проверок.

Интерфейс должен поддерживать увеличение текста, экранный диктор и понятные пользовательские сценарии.

## Решение

Приложение использует упрощённую Clean Architecture с организацией исходного кода по функциям.

Основные функциональные области:

- `library` — музыкальная библиотека.
- `playback` — воспроизведение и очередь.
- `playlists` — пользовательские плейлисты.
- `history` — история воспроизведения.

Каждая область разделяет четыре ответственности.

### Domain

Слой `domain` содержит модели и бизнес-правила.

Он использует чистые типы и функции TypeScript. Он независим от React Native, Android, SQLite и конкретного аудиодвижка.

### Application

Слой `application` содержит пользовательские сценарии и контракты необходимых зависимостей.

Примеры сценариев:

- Создание плейлиста.
- Добавление песни в плейлист.
- Запуск воспроизведения.
- Регистрация события в истории.

Сценарии получают зависимости явно. Интерфейсы репозиториев и платформенных операций размещаются в `application/ports`.

### Infrastructure

Слой `infrastructure` реализует контракты приложения.

Его ответственность включает хранение данных, получение музыкальной библиотеки и взаимодействие с аудиодвижком.

Android-модули на Kotlin предоставляют необходимые платформенные операции. Их использование из TypeScript проходит через
инфраструктурные адаптеры.

### Presentation

Слой `presentation` содержит экраны, компоненты и состояние интерфейса.

Интерфейс декларативно отображает состояние. Пользовательские действия вызывают сценарии слоя `application`.

Компоненты независимы от конкретных реализаций репозиториев и аудиодвижка.

### Сборка приложения

Каталог `app` содержит точку сборки зависимостей, провайдеры и настройку навигации.

Конкретные реализации передаются сценариям приложения через их контракты.

Поток взаимодействия:

```text
Действия пользователя
    → сценарий приложения
    → изменение состояния
    → отображение интерфейса
```

Фоновые события воспроизведения также вызывают сценарии приложения. Запись истории работает независимо от наличия открытого
экрана.

## Направление зависимостей

- `domain` содержит независимые модели и правила.
- `application` зависит от `domain`.
- `infrastructure` реализует контракты `application` и использует модели `domain`.
- `presentation` использует публичные сценарии и модели.
- `app` связывает слои конкретными реализациями.

Функциональные области взаимодействуют через явно определённые публичные контракты.

Циклические зависимости между областями запрещены. Обращение к внутренним инфраструктурным реализациям другой области
запрещено.

## Целевая организация кода

```text
src/
    app/
    features/
        library/
        playback/
        playlists/
        history/
    shared/
```

Пример структуры функциональной области:

```text
playlists/
    domain/
    application/
        ports/
    infrastructure/
    presentation/
```

Каталоги создаются по мере появления соответствующего кода.

`shared` содержит повторно используемые компоненты и независимые утилиты. Бизнес-правила сохраняются в соответствующих
функциональных областях.

## Тестирование

Unit-тесты проверяют бизнес-правила и сценарии приложения.

Integration-тесты проверяют взаимодействие реальных модулей. Подмена внешней границы явно обозначается в тестовом сценарии.

Работа реального хранилища, Android-модулей и фонового воспроизведения проверяется отдельно в Android-окружении.

Тесты описываются в стиле Given / When / Then и содержат явные проверки ожидаемого результата.

## Последствия

- Бизнес-правила можно проверять независимо от мобильного окружения.
- Замена хранилища или аудиодвижка ограничивается соответствующими адаптерами.
- Интерфейс и фоновые обработчики используют общие сценарии приложения.
- Для каждой внешней зависимости требуется поддерживать контракт и реализацию.
- Разработчик должен соблюдать границы слоёв и контролировать зависимости.
- Изменения архитектурных границ фиксируются отдельным ADR.

## Рассмотренные альтернативы

### Размещение логики в экранах и компонентах

Подход сокращает начальную организацию кода, но связывает бизнес-правила с жизненным циклом интерфейса и усложняет проверку
фонового поведения.

### Организация только по техническим категориям

Общие каталоги компонентов, сервисов и моделей разделяют код по типу. При развитии приложения изменения одной функции
распределяются по нескольким общим каталогам.

Выбрана организация по функциям с едиными границами слоёв.

## Последующие решения

Выбор аудиодвижка, библиотеки доступа к SQLite и правил учёта истории оформляется отдельными ADR.
