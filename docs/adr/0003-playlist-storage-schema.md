# ADR-0003: Схема хранения плейлистов и миграции

## Статус

Принято.

## Контекст

На момент принятия решения приложение содержит модель плейлиста, контракт `PlaylistRepository` и реализацию репозитория
в памяти.

Работа SQLite на Android проверена отдельно. Рабочая схема хранения плейлистов отсутствует.

Плейлист содержит идентификатор, название и упорядоченный список идентификаторов композиций. Постоянное хранилище сохраняет
все данные этой модели.

Изменение структуры базы требует сохранения существующих пользовательских данных между версиями приложения.

## Решение

### Рабочая база

Данные приложения размещаются в файле `music-player.sqlite`.

Диагностическая база `musicPlayer-storage-check.sqlite` остаётся отдельной и не используется для пользовательских данных.

Точка сборки приложения открывает рабочую базу, выполняет её инициализацию и передаёт готовое соединение репозиториям.

Репозитории используют переданное соединение и не закрывают его после отдельных операций.

При ошибке инициализации соединение закрывается. Репозитории не получают неинициализированную базу.

### Плейлисты

Таблица `playlists` содержит следующие обязательные поля:

- `id` — текстовый идентификатор плейлиста и первичный ключ.
- `name` — текстовое название плейлиста.

Названия не имеют ограничения уникальности.

Нормализация и проверка названия остаются ответственностью `domain`.

### Композиции в плейлистах

Таблица `playlist_tracks` содержит следующие обязательные поля:

- `playlist_id` — идентификатор плейлиста.
- `position` — целочисленная позиция композиции, начиная с нуля.
- `track_id` — текстовый идентификатор композиции.

Первичный ключ состоит из `playlist_id` и `position`.

Поле `playlist_id` ссылается на `playlists.id`. Удаление записи плейлиста каскадно удаляет связанные записи `playlist_tracks`.

Поле `position` имеет ограничение на неотрицательное значение. При сохранении массива репозиторий назначает последовательные
позиции.

Идентификатор композиции может встречаться на разных позициях. Хранилище сохраняет последовательность `trackIds` без удаления
повторений.

Пустой плейлист представлен записью в `playlists` без связанных записей в `playlist_tracks`.

Связь `track_id` с таблицей музыкальной библиотеки определяется отдельным решением после появления модели библиотеки.

Схема связей представлена на [диаграмме версии 1](../diagrams/database/playlists-v1.puml).

### Миграции

Версия схемы хранится в `PRAGMA user_version`.

Версия `0` обозначает базу до применения первой миграции. Первая миграция создаёт таблицы `playlists` и `playlist_tracks`
и устанавливает версию `1`.

Миграции имеют последовательные номера и выполняются в порядке возрастания. Уже применённые миграции повторно не выполняются.

Изменения каждой миграции и обновление версии выполняются в одной транзакции.

При ошибке изменения этой миграции откатываются. Инициализация базы завершается ошибкой.

Если версия базы превышает поддерживаемую приложением, инициализация завершается ошибкой. Автоматическое понижение версии
и пересоздание базы не выполняются.

Применённые миграции сохраняются без изменений. Последующие изменения схемы оформляются новыми миграциями.

Проверка внешних ключей явно включается для каждого соединения командой `PRAGMA foreign_keys = ON` до начала транзакций.

### Сохранение плейлиста

Добавление плейлиста и всех его композиций выполняется в одной транзакции.

Ошибка любой записи отменяет всю операцию.

Повторный идентификатор плейлиста приводит к ошибке без замены существующих данных.

## Рассмотренные альтернативы

### Хранение `trackIds` в JSON

JSON сохраняет порядок массива. Отдельная таблица упрощает задание ограничений и связей для отдельных записей.

Отдельная таблица явно представляет принадлежность композиции плейлисту и её позицию.

### Пересоздание базы при изменении схемы

Подход упрощает изменение структуры, но приводит к потере пользовательских данных.

Версионированные миграции сохраняют данные между изменениями схемы.

## Последствия

- Хранилище сохраняет все поля существующей модели плейлиста.
- Порядок композиций представлен явно.
- Для сохранения и чтения плейлиста требуется работа с двумя таблицами.
- Транзакции защищают от частичного сохранения.
- Изменения схемы требуют новых миграций и проверок сохранности данных.
- Более новая база не открывается для работы неподдерживаемой версией приложения.

## Не входит в решение

- Схема музыкальной библиотеки.
- Схема истории воспроизведения.
- Пользовательские сценарии добавления и удаления композиций.
- Интерфейс управления плейлистами.
- Резервное копирование и синхронизация данных.
