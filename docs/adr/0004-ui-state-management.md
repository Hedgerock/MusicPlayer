# ADR-0004: Управление состоянием интерфейса

## Статус

Принято.

## Контекст

На момент принятия решения приложение использует локальное состояние React. Рабочая база SQLite подключена к запуску
приложения. Внешний менеджер состояния отсутствует.

Приложение предусматривает музыкальную библиотеку, плейлисты, историю и несколько представлений плеера.

Локальные формы требуют собственного состояния. Представления плеера требуют согласованных данных о текущем воспроизведении.

Обработка фоновых событий воспроизведения должна работать независимо от наличия открытого экрана.

Сохранённые данные, фактическое состояние аудиодвижка и состояние интерфейса имеют разные источники и время жизни.

## Решение

### Локальное состояние

Состояние, необходимое одному компоненту или экрану, размещается рядом с его владельцем.

Простое локальное состояние управляется через `useState`.

Связанные переходы состояния, требующие согласованного обновления нескольких значений, могут управляться через `useReducer`.

Выбор между `useState` и `useReducer` определяется сложностью переходов.

Состояние нескольких связанных компонентов поднимается к ближайшему владельцу, если его время жизни и область использования
соответствуют этому владельцу.

Значения, вычисляемые из существующих props и state, рассчитываются при отображении. Отдельное состояние для них не создаётся.

### Общее состояние

Для общего состояния интерфейса, используемого несколькими экранами и независимыми компонентами, выбран Zustand.

Первое применение библиотеки связано со сценарием, которому требуется такое состояние. Наличие локального состояния формы
не является основанием для создания общего store.

Общее состояние разделяется по функциональным областям. Store создаются по мере появления соответствующих сценариев.

Компоненты подписываются на необходимые части состояния через селекторы.

Context используется для передачи подготовленных зависимостей сценариев и общей конфигурации.

### Источник данных

Сохранённые плейлисты и история хранятся в SQLite. Операции чтения и изменения выполняются через контракты и сценарии
приложения.

Интерфейс может хранить загруженный снимок данных для отображения.

После успешного изменения сохранённых данных соответствующий снимок обновляется либо помечается неактуальным и загружается
повторно.

Фактические сведения о воспроизведении поступают от аудиодвижка. Общее состояние интерфейса содержит их представление для
отображения.

Отправка команды воспроизведения и подтверждение её выполнения рассматриваются как разные события.

Обработка событий воспроизведения и регистрация истории имеют время жизни, определяемое приложением и платформенным окружением.
Их выполнение не зависит от монтирования отдельных экранов.

### Граница слоёв

Слои `domain` и `application` сохраняют независимость от React и Zustand.

Хранилища состояния интерфейса и React-хуки размещаются в `presentation` соответствующей функциональной области.

Бизнес-правила остаются в `domain`. Пользовательские сценарии остаются в `application`.

Каталог `app` связывает сценарии, инфраструктурные реализации и состояние представления.

Функциональные области взаимодействуют через публичные контракты. Прямое обращение к внутреннему store другой области не
используется.

Практические правила компонентов, хуков, мемоизации и эффектов определены в
[руководстве по слою представления](../rules/react-presentation-guidelines.md).

## Рассмотренные альтернативы

### Только локальное состояние и Context

Подход подходит для локальных форм и передачи зависимостей.

Для общего состояния плеера выбрана библиотека с подписками на отдельные части состояния и доступом к store вне React-компонентов.

### Redux Toolkit

Redux Toolkit предоставляет модель действий, reducer и инструменты для организации общего состояния.

Для общего состояния интерфейса выбран Zustand с компактным API подписок и обновлений. Границы ответственности и правила
организации состояния задаются архитектурой проекта.

## Последствия

- Локальные формы сохраняют состояние рядом с местом использования.
- Представления плеера используют согласованный снимок состояния воспроизведения.
- Обновление состояния требует контроля состава подписок.
- Снимки данных SQLite требуют явного обновления после изменений.
- Бизнес-правила проверяются независимо от React и менеджера состояния.
- Общее состояние требует отдельных проверок переходов и согласованности данных.

## Не входит в решение

- Выбор аудиодвижка.
- Реализация фонового воспроизведения.
- Правила восстановления очереди и позиции воспроизведения.
- Реализация конкретных store.
- Конкретная версия Zustand и её подключение.
- Подробности реализации пользовательских экранов.
