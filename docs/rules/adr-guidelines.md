# Правила написания ADR

## Назначение

ADR фиксирует архитектурный выбор, причины его принятия и последствия для проекта.

Планы реализации и критерии приёмки размещаются в спецификациях функций. Результаты проверок размещаются в документации
по тестированию. Завершённые изменения отражаются в `CHANGELOG.md`.

ADR создаётся для решений, которые определяют архитектурные границы, ключевые зависимости, модели данных или долгосрочные
ограничения.

## Размещение

Архитектурные решения находятся в `docs/adr/`.

Индекс решений находится в `docs/adr/README.md`.

Файл ADR имеет имя `XXXX-short-decision-name.md`. Номер содержит четыре цифры, название записывается на английском языке
в kebab-case.

Нумерация сквозная. Назначенные номера сохраняются и повторно не используются.

Относительные ссылки разрешаются от директории документа.

## Язык и оформление

ADR и индекс решений относятся к внутренней документации и пишутся на русском языке.

Заголовок имеет формат: `ADR-XXXX: Краткое название решения`.

Основные разделы используют заголовки второго уровня. Подразделы используются при необходимости.

Текст состоит из коротких декларативных абзацев. Каждый абзац раскрывает одну мысль.

Предложения и пункты списков заканчиваются точкой. Заголовки записываются без точки.

Имена типов, методов, библиотек и пути выделяются обратными кавычками и сохраняют написание из проекта.

Небольшие схемы взаимодействия допускаются. Большие фрагменты кода размещаются в исходных файлах.

## Статусы

- Предложено — решение рассматривается.
- Принято — архитектурный выбор согласован.
- Отклонено — предложенный выбор отклонён.
- Заменено — действует другое решение, указанное ссылкой.

Статус отражает состояние архитектурного выбора. Готовность реализации фиксируется отдельно.

## Структура ADR

Разделы располагаются в следующем порядке:

1. Статус.
2. Контекст.
3. Решение.
4. Рассмотренные альтернативы — при необходимости.
5. Последствия.
6. Не входит в решение.
7. Связанные решения.
8. Источники — при необходимости.

Если связанных решений нет, раздел содержит формулировку "Отсутствуют".

## Содержание разделов

Контекст описывает проблему и состояние проекта на момент принятия решения. Он указывает затронутые зоны ответственности и
ограничения.

Для исторического состояния используется формулировка "на момент принятия решения". Формулировки "сейчас" и "на текущем этапе"
не используются.

Решение определяет выбранный подход, распределение ответственности, границы компонентов и действующие контракты.

Формулировки решения задают архитектурные правила. Фактическая готовность компонентов указывается в документации по реализации.

Рассмотренные альтернативы объясняют выбор между реалистичными вариантами. Раздел добавляется, когда причины отклонения вариантов
помогают понять решение.

Последствия описывают преимущества, ограничения, стоимость поддержки и влияние на существующие сценарии.

Раздел "Не входит в решение" перечисляет связанные темы, которые требуют отдельного решения или спецификации.

Связанные решения содержат ссылки на ADR с кратким пояснением связи.

Источники содержат ссылки на документацию, исследования и результаты проверок, повлиявшие на выбор.

## Связь с реализацией

После статуса допускается короткое примечание со ссылкой на значимый результат реализации или проверки.

Примечание обновляется при существенном изменении состояния. Количество коммитов не является условием его добавления.

Подробный прогресс и перечни выполненных задач ведутся в соответствующих спецификациях и CHANGELOG.

## Изменение принятых решений

Принятый ADR сохраняет исходный контекст и причины выбора.

Исправления опечаток, оформления и ссылок допускаются при сохранении смысла.

Изменение архитектурного выбора оформляется новым ADR.

Заменённое решение получает статус "Заменено" и ссылку на новый ADR. Новый ADR содержит обратную ссылку. Индекс решений
обновляется.

Существующие ADR могут приводиться к единой структуре отдельной документационной правкой. Их исторический контекст и смысл
решения сохраняются.
