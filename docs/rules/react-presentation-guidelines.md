# Правила разработки слоя представления React

## Назначение

Документ определяет правила организации компонентов, пользовательских хуков, состояния, мемоизации и эффектов.

Распределение состояния между React, Zustand и постоянным хранилищем определяется [ADR-0004](../adr/0004-ui-state-management.md).

## Ответственность представления

Компоненты отображают состояние и предоставляют доступные пользователю действия.

Пользовательские действия вызывают сценарии слоя `application`.

Бизнес-правила сохраняются в `domain`. SQL-запросы и непосредственное взаимодействие с аудиодвижком размещаются в
инфраструктурных реализациях.

Зависимости сценариев подготавливаются в `app` и передаются явно через props или Context.

Вычисления при рендере являются чистыми. Входные props и существующее состояние не изменяются напрямую.

## Декомпозиция компонентов

Компонент имеет понятную ответственность и имя, отражающее его назначение.

Основанием для выделения компонента являются:

- Самостоятельная часть пользовательского интерфейса.
- Повторное использование одинакового поведения.
- Собственное локальное состояние или подписка.
- Сложная разметка, затрудняющая чтение основного сценария экрана.
- Самостоятельный контракт доступности.

Количество строк используется как сигнал для анализа. Фиксированный размер компонента не является обязательным условием
разделения.

Небольшая разметка, которая остаётся понятной в родительском компоненте, может сохраниться в нём.

Компоненты объявляются на уровне модуля. Объявление компонента внутри функции другого компонента не используется.

При разделении сохраняются пользовательская семантика и порядок взаимодействия.

Иконка и подпись одной кнопки образуют одно действие. Декомпозиция не создаёт лишние остановки фокуса для TalkBack.

## Размещение файлов

Экраны размещаются в `presentation/screens` соответствующей функциональной области.

Компоненты, используемые только одним экраном, размещаются рядом с ним.

Компоненты нескольких экранов одной области размещаются в её `presentation/components`.

В `shared/ui` размещаются компоненты с общим контрактом, используемые несколькими функциональными областями. Эти компоненты
независимы от бизнес-правил областей.

Хук одного экрана размещается рядом с экраном. Хуки нескольких компонентов одной области размещаются в её `presentation/hooks`.

Пример организации:

```text
src/
  features/
    playlists/
      presentation/
        screens/
          create-playlist-screen/
            create-playlist-screen.tsx
            use-create-playlist.ts
            components/
              playlist-name-field.tsx
            __tests__/
              create-playlist-screen.test.tsx
        components/
          playlist-list-item.tsx
        hooks/
          use-playlists.ts
  shared/
    ui/
      app-button.tsx
```

Каталоги создаются по мере появления соответствующего кода.

Имена файлов записываются в kebab-case.
Имена React-компонентов записываются в PascalCase.

Тип props размещается рядом с компонентом. Стили первоначально размещаются в файле компонента.

Отдельный файл стилей используется, когда это улучшает читаемость.

Импорты следуют [правилам оформления импортов](import-guidelines.md).

## Стили

Стили нативных компонентов описываются типизированными объектами через `StyleSheet.create`.

CSS-файлы для Android- и iOS-компонентов не используются.

Небольшой набор стилей размещается в файле компонента.

Стили выносятся в соседний файл `<component-name>.styles.ts`, когда это улучшает читаемость компонента или упрощает работу
с вариантами оформления.

Количество строк само по себе не определяет необходимость отдельного файла.

Отдельный файл стилей принадлежит своему компоненту. Перенос стилей в общий каталог требует подтверждённого повторного
использования и общего визуального контракта.

Общие значения цветов, размеров и отступов выделяются при появлении повторяющихся требований.

Стили сохраняют поддержку системного увеличения шрифта. Фиксированные размеры не обрезают текст и не скрывают действия.

Минимальная область нажатия задаётся независимо от размера текста.

## Локальное состояние

Состояние размещается у ближайшего владельца, которому оно необходимо.

Введённое значение формы, ошибка ввода и состояние отправки сохраняются локально, если сценарий не требует общего владельца.

Связанные переходы состояния выражаются согласованной моделью. Использование нескольких независимых флагов не должно допускать
противоречивые состояния.

`useReducer` применяется, когда явные действия и переходы делают управление состоянием понятнее.

Производные значения рассчитываются из существующих данных при рендере.

Редактируемый черновик может содержать копию исходных данных. Для него явно определяются правила инициализации, сохранения
и сброса.

## Пользовательские хуки

Пользовательский хук выделяется для самостоятельной логики, использующей состояние, эффекты, refs или другие возможности
React.

Основаниями для выделения хука являются повторное использование логики, управление связанным поведением и отделение
взаимодействия от разметки.

Хук может использоваться одним компонентом.

Обязательное создание отдельного хука для каждого компонента не требуется.

Имя хука начинается с `use` и описывает назначение. Примеры: `useCreatePlaylist`, `usePlaybackProgress`.

Хук представления управляет состоянием интерфейса и вызывает подготовленные сценарии приложения.

Чистые вычисления, которым не требуются возможности React, оформляются обычными функциями.

Локальное состояние внутри каждого вызова хука независимо. Общее состояние предоставляется через явного владельца или store.

Обёртки жизненного цикла вроде `useMount` и `useEffectOnce` не используются. Хук описывает конкретное поведение и сохраняет
явные зависимости.

## Мемоизация

Компоненты и вычисления первоначально реализуются без ручной мемоизации.

Мемоизация добавляется для конкретной проблемы производительности. Причина применения и эффект оптимизации подтверждаются
измерениями.

| Инструмент    | Назначение                                                             |
| ------------- | ---------------------------------------------------------------------- |
| `memo`        | Позволяет пропускать повторный рендер компонента при неизменных props. |
| `useMemo`     | Кэширует результат чистого вычисления между рендерами.                 |
| `useCallback` | Сохраняет ссылку на функцию между рендерами.                           |

### memo

`memo` применяется, когда компонент повторно получает одинаковые props, а его рендер имеет заметную стоимость.

Состав props и стабильность передаваемых ссылок учитываются при оценке оптимизации.

Изменение собственного состояния или используемого Context может вызывать рендер мемоизированного компонента.

Пользовательское сравнение props применяется только при обоснованной необходимости. Сравнение учитывает все значения,
влияющие на отображение и поведение.

### useMemo

`useMemo` применяется для дорогих вычислений либо сохранения ссылки, когда это даёт пользу потребителю результата.

Простые вычисления первоначально выполняются непосредственно при рендере.

Функция вычисления не выполняет побочные действия.

Открытие базы, создание подписок и запись данных не размещаются в `useMemo`.

Корректность программы не зависит от сохранения кэша. Время жизни ресурсов управляется явно.

### useCallback

`useCallback` применяется, когда стабильность ссылки на функцию необходима потребителю или позволяет получить подтверждённую
пользу от мемоизации.

Обработчики событий не оборачиваются в `useCallback` автоматически.

## useEffect

`useEffect` используется для синхронизации представления с внешней системой.

Подходящие случаи включают:

- Подписку на внешние события.
- Загрузку данных для отображаемого экрана.
- Управление таймером, связанным с жизнью компонента.
- Ожидание готовности внешнего хранилища на уровне приложения.

Каждый эффект имеет одну понятную цель синхронизации.

Зависимости содержат используемые реактивные значения. Предупреждения о зависимостях не подавляются ради однократного запуска.

Эффект сохраняет корректность при повторной установке после очистки.

Очистка освобождает ресурсы, которыми владеет эффект. Подписки отменяются, таймеры останавливаются.

Компонент не закрывает общее соединение базы, время жизни которого управляется приложением.

Асинхронные операции запускаются внутри эффекта. Сам callback эффекта не объявляется `async`.

Устаревшие асинхронные результаты не обновляют неактуальное состояние интерфейса. Используется отмена операции, если она
поддерживается, либо игнорирование результата.

Эффект не используется для:

- Вычисления производных значений из props и state.
- Фильтрации уже загруженных данных перед отображением.
- Запуска пользовательского сценария по флагу, установленному обработчиком кнопки.
- Создания цепочки изменений локального состояния, вычисляемой в одном обработчике или reducer.
- Дублирования props в state без самостоятельного сценария редактирования.

Действия, вызванные нажатием пользователя, обрабатываются в соответствующих обработчиках.

Запись истории воспроизведения не запускается наблюдением за состоянием экрана. Она выполняется через сценарий приложения при
обработке фактического события воспроизведения.

## Доступность

Элементы управления имеют понятные роли, подписи и состояния.

Основные действия имеют видимый текст.

Область нажатия составляет не менее 48 x 48 dp.

Системное увеличение шрифта сохраняет читаемость и доступность действий.

Сообщения об ошибках доступны через TalkBack. Ошибка обозначается текстом и содержит доступное следующее действие.

## Проверка поведения

Компонентные тесты находят элементы по доступной роли и названию. Сообщения проверяются по видимому тексту.

Тесты проверяют наблюдаемое поведение пользователя.

Самостоятельная сложная логика хуков может проверяться через `renderHook`. Чистые функции проверяются юнит-тестами.

При декомпозиции существующие проверки поведения сохраняются.

Мемоизация оценивается измерениями производительности. Количество вызовов рендера не подменяет проверку пользовательского
поведения.

Общие требования к тестированию определены в [CONTRIBUTING](../../CONTRIBUTING.md).

## Визуальные проверки

Скриншотные тесты сравнивают изображения интерфейса, отрисованного на устройстве или эмуляторе.

Такие тесты добавляются для стабильных экранов после подключения к нативному приложению.

Приоритетные сценарии включают основные состояния экрана, длинные названия, увеличенный системный шрифт и ограниченную ширину
экрана. Проверки тем добавляются после реализации соответствующих тем.

Каждый профиль проверки фиксирует версию Android, конфигурацию эмулятора, разрешение и плотность экрана, масштаб шрифта,
язык и тему.

Тестовые данные воспроизводимы. Снимок создаётся после завершения загрузки и анимаций.

Изменения эталонных изображений проверяются вручную. Обновление эталона сопровождается объяснением ожидаемого изменения
интерфейса.

Снимки дерева компонентов в Jest не считаются скриншотными тестами.

Визуальные проверки дополняют тесты поведения и ручные проверки доступности. Корректное изображение не подтверждает работу
TalkBack, порядок фокуса или доступность действий.

Инструмент и способ запуска скриншотных тестов определяются при добавлении первого подтверждённого сценария.
